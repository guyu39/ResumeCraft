## Context

`job_applications` 当前同时要求 `resume_id` 和 `snapshot_version_id` 非空，创建 Service 与 Repository 也把两者视为一个不可拆分的关联。简历版本重构后，新建简历只有内部 `current` 工作副本，而投递 Repository 正确地禁止绑定 `current`，导致职位无法先进入待适配管道。

AI 匹配请求直接携带完整简历正文，`job_application_ai_runs.source_snapshot_version_id` 和检查清单来源快照已经允许为空，因此投递主表没有技术必要强制快照存在。

## Goals / Non-Goals

**Goals:**

- 职位可以只关联简历进入待适配管道，快照可稍后绑定、替换或清除。
- 保持现有已关联记录、AI 结果、检查清单、漏斗、导出和删除保护兼容。
- 明确定义更换简历、空关联和非法快照的更新语义。
- 不把内部 `current` 工作版本暴露为可投递快照。

**Non-Goals:**

- 本变更不修改简历创建时是否生成 `default` 分支。
- 不自动创建“投递记录”快照，不冻结已投递时的简历正文。
- 不新增状态流转阻断、弹窗确认或快照版本选择页面。
- 不改变快照本身的可变分支语义。

## Decisions

### 1. 简历必填，快照可空

数据库允许 `job_applications.snapshot_version_id` 为 NULL。API 创建请求中的 `snapshotVersionId` 可省略或为空；响应缺少关联时返回 null。这样职位记录仍有明确的简历上下文，但不会要求用户提前决定版本。

不采用绑定 `current_version_id` 的方案，因为 `current` 在分支切换时会承载不同内容，无法稳定代表投递版本。

### 2. 更新使用“未提供、空值、非空值”三态

- 未提供 `snapshotVersionId` 且简历未变：保留现有关联。
- 提供空字符串：清除快照关联。
- 提供非空 ID：校验快照属于目标简历和当前用户，且类型不是 `current`，通过后替换关联。
- 更换 `resumeId` 且未同时提供快照：自动清空原快照，防止旧快照跨简历残留。

Go Request 使用 `*string` 区分字段未提供与显式空字符串；Repository 参数使用显式布尔标记，不依赖字符串是否为空推断更新意图。

### 3. AI 来源不追溯改写

未绑定快照时，创建请求携带的 match/score 结果仍生成 AI run 和检查清单，其 `source_snapshot_version_id` 保存 NULL。用户后续绑定快照不会修改既有 AI 运行来源；重新生成检查清单时使用投递记录当时的可选快照 ID。

这保留了来源真实性，避免把后绑定版本错误标记为旧分析的输入版本。

### 4. NULL 在展示和统计中有稳定语义

列表与详情响应使用可空 `snapshotVersionId`，标签为空时前端和 Excel 显示“未关联版本”。按快照转化统计保留 NULL 分组并将其标签设为“未关联版本”，避免分组总数与漏斗总数不一致。

### 5. 前端不自动选择快照

选择简历后加载可用快照，但表单默认保持“暂不关联版本”。编辑已有记录时保留其当前关联；用户可在选择器中显式选择“暂不关联版本”清除关联。没有快照时仍正常提交，不展示阻断式警告。

## Risks / Trade-offs

- [未关联记录无法按版本复盘] → 转化统计明确归入“未关联版本”，用户可后续补充关联。
- [后绑定版本与实际投递版本不一致] → 产品允许修改关联，本变更不宣称关联是不可变历史证据。
- [NULL 导致现有字符串扫描失败] → 所有主表列表、详情、重复查询、统计和导出扫描统一使用 nullable 扫描或 SQL COALESCE。
- [更换简历遗留旧快照] → Repository 在同一事务内计算目标简历与目标快照并校验后更新。

## Migration Plan

1. 执行幂等迁移，去除 `job_applications.snapshot_version_id` 的 NOT NULL 约束；不新增外键。
2. 发布后端，使创建、更新、查询、AI 来源和统计兼容 NULL。
3. 发布前端，提供“暂不关联版本”并移除快照必填校验。
4. 验证已有非空关联数量与标签未变化，并验证 NULL 分组统计。

回滚时，若已经产生 NULL 记录，旧后端无法安全读取且旧约束无法直接恢复。回滚前必须先为 NULL 记录补齐有效快照或删除相关测试记录，因此本变更按数据库、后端、前端顺序发布，不建议只回滚应用。
