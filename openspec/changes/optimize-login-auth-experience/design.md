## Context

登录页同时承载认证与产品介绍。现状以固定定位、透明度和 `pointer-events` 在桌面端切换两组介绍内容，并监听滚轮改变相位；认证表单本身缺少自动填充及错误关联语义。认证 API、Zustand 状态、验证码倒计时、会话失效提示和顶号确认均已稳定，本次只调整页面结构和客户端校验。

## Goals / Non-Goals

**Goals:**

- 让认证表单在桌面和移动端都成为明确的第一操作任务。
- 让浏览器密码管理器、验证码自动填充和辅助技术能正确识别每个字段。
- 让所有提交前错误就近显示，并将焦点落到首个无效字段。
- 在不增加装饰噪音的前提下准确说明产品当前三个完整闭环。
- 保持现有认证和安全回跳行为不变。

**Non-Goals:**

- 不新增忘记密码、社交登录或新的认证接口。
- 不修改认证状态管理、后端校验规则或验证码发送策略。
- 不引入真实产品截图、图片资源或新的 UI 依赖。

## Decisions

1. **使用单一 DOM 布局替代相位切换。** 页面根节点采用响应式双栏布局，桌面左侧为品牌与三条能力说明、右侧为认证表单；移动端通过 CSS 顺序让品牌简写和表单先于能力说明。相比继续修补透明度和 `tabIndex`，移除隐藏相位能从根源上消除不可见焦点与滚轮接管。
2. **字段错误由当前表单状态计算，展示由 touched 控制。** 提交时一次性标记当前模式的必填字段；失焦只标记单字段。空值、格式、长度和一致性错误共用同一错误出口，避免 Toast 与字段错误表达不一致。
3. **使用原生字段语义与 ARIA 关联。** 每个输入有稳定 `id`/`name`/`autoComplete`，错误节点使用 `${id}-error`，仅在错误可见时设置 `aria-describedby`，并通过 `aria-invalid` 暴露状态。登录方式使用 `tablist`/`tab`/`aria-selected`。
4. **密码显示状态按字段独立维护。** 登录/注册密码与确认密码分别使用 `Eye`/`EyeOff` 图标按钮；按钮带 `aria-label` 和 `title`，不会提交表单。
5. **保留弱打扰反馈分工。** 字段问题使用内联红字，验证码发送、接口失败和认证结果继续使用 Toast。提交按钮文案根据模式显示明确动作。
6. **产品能力使用无卡片列表。** 三条能力说明配合现有 Lucide 图标，使用中性灰背景和项目蓝色作为小面积强调，不使用渐变光斑、玻璃拟态或嵌套卡片。

## Risks / Trade-offs

- [移动端注册表单较长，能力说明可能落到首屏以下] -> 表单优先符合页面核心任务，页面保留原生纵向滚动。
- [浏览器对 `one-time-code` 的桌面支持不一致] -> 属性仍提供标准语义，数字输入和长度限制继续由前端保证。
- [删除登录页专用动画可能误伤其他页面] -> 删除前按类名全仓检索，仅清理无其他引用的规则。
- [客户端校验与服务端文案可能不同] -> 客户端只处理明确的必填和格式规则，服务端错误继续通过 Toast 原样反馈。

## Migration Plan

无需数据迁移。前端部署后直接生效；如需回滚，只需恢复登录页组件与对应的登录页专用 CSS。
